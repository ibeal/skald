## Acceptance criteria

**Context.** This is the slice that pays for itself immediately, and it is the "test, not prose" half
of the enforcement story: instructions describe the contract, `check` is what fails when the contract
is broken. It is also what makes the migration tractable — every existing ticket in every store is
currently non-conforming, and `check` is how you see the whole list.

### Validation

- `skald check [--fix]` validates every ticket in `$SKALD_STORE` against the contract compiled into
  skald. There is no schema file to read.
- Report **every** violation per ticket, not just the first, and name `file:line` so each is
  navigable.
- Frontmatter violations:
  - unknown key — the field set is closed, so an unknown key is a violation rather than an extension
  - missing required key (`title`, `status`, `repos`, `created`, `updated`)
  - empty value where the field may not be empty (`title`, `status`, `created`, `updated`)
  - **`status` outside the enum, including a valid value with decoration appended** — `building
    (pending Ian)` is the case that motivated the whole tool
  - malformed date in `created`/`updated`
  - `pr`, `link` present but not an absolute http(s) URL
  - `parent` naming a ticket that does not exist in this store
- Body violations:
  - `## Acceptance criteria` missing
  - `## Log` missing
  - a top-level section that is neither — the body is closed, so an unrecognized `##` heading is a
    violation rather than an extension. Only that level is checked; `###` and below inside a section
    belong to the author.
  - an H1 present — `title` is frontmatter, and an H1 is the old shape
- **Exit non-zero on any violation** so a pre-commit hook or CI step can gate on it. Exit 0 and print
  nothing when clean. Use a distinct exit code for "violations found" versus "skald itself failed",
  matching `rata doctor`.

### `--fix` is deliberately narrow

`--fix` repairs only what is unambiguously mechanical, and **never guesses at a `status` value.**
`building (pending Ian)` is reported, never silently rewritten to `building`, because the qualifier is
information and discarding it is data loss — the human moves it to the log. What it may do:

- trim surrounding whitespace from a value
- normalize a date to `YYYY-MM-DD` where the intent is unambiguous
- add a missing required key with an empty value, so the shape is right and the violation becomes
  "empty" rather than "absent"
- add a missing `## Acceptance criteria` or `## Log` heading
- **lift a leading H1 into `title:`** when `title` is absent — the one semantic fix worth having,
  because it is exactly the migration every existing ticket needs and it is unambiguous

Everything else is reported for a human. Document the pre-commit hook invocation in the README; do
not install it.

**Explicitly out of scope:**

- Enforcing that agents *use* skald. That is the permission deny, in the parent's rollout.
- Enforcing the status *transition* rules. `done` and `cancelled` being terminal is enforced by `set`
  at write time; `check` reads a file with no knowledge of what it was before, so it cannot judge a
  transition.
- Rewriting `phase` → `status`, `projects` → `repos`, or `source`/`spec` → `link`. Those renames are
  the migration's job, not a validator's, and guessing a status from an old phase is exactly the kind
  of inference `--fix` must not make.

**Verification:** run against this repo's store — it passes clean. Run against
`dotfiles/agents/tickets` un-migrated: it reports every ticket, names the unknown keys and the missing
`title`, and exits non-zero. A deliberately broken fixture exits non-zero. `--fix` on a decorated
`status` leaves it untouched and still exits non-zero. `--fix` on a ticket with an H1 and no `title`
produces a valid ticket.

- 2026-08-20: Built. Exit 2 for "the store is invalid", 1 for "skald itself failed", so a hook can
  tell them apart. Broken frontmatter reports only the one thing worth saying rather than the twelve
  missing keys underneath it, because the twelve would bury the actual problem.
- 2026-08-20: **Deviation from the AC, deliberate.** The AC asked `--fix` to trim whitespace around a
  value. It doesn't, and shouldn't: padding is not a violation — the parser reads the trimmed value,
  so `check` reports nothing — and rewriting it would collapse deliberate alignment, which is exactly
  the byte-preservation the round-trip guarantee exists to provide. A fix that repairs nothing and
  destroys something is not a fix. Found by writing the test for it. The AC is stale on this point;
  flagged to Ian rather than edited, since this ticket is `building` and the criteria are frozen.
- 2026-08-20: Two bugs the migration rehearsal caught, both invisible to the unit tests as first
  written. Keys added by `--fix` were inserted one at a time and so all anchored on the same byte,
  coming out in call order rather than contract order — a repaired ticket read like a repaired one.
  And an H1 holding *only* the ticket id (`# ask-2026-07-23-install-helix`) produced
  `title: ask-2026-07-23-install-helix`, putting a non-title in the field a human reads first. It now
  removes the heading, adds no title, and lets `check` report the empty one — which is the honest
  outcome and the one that prompts a human to write a real title.
- 2026-08-20: Rehearsed against copies of two real un-migrated tickets. `check` names every violation
  with a navigable line; `--fix` repairs shape and leaves `phase`, `## Build log`, and every decorated
  value untouched, still exiting non-zero. That is the intended division: shape is mechanical, meaning
  is a human's.
- 2026-08-20: cleared parent: the parent ticket lives in the dotfiles store, and parent is same-store by design since that is what --parent filters on. The relationship is stated in the AC context instead.
- 2026-08-20: Fresh-eyes review, all findings fixed. Two were mine to be embarrassed by. --fix added a missing created: as empty, but created may not be empty and no command can set it, so a repaired legacy ticket became permanently unwritable -- the exact input the fix exists to rescue. It now takes the file's mtime, which is the best evidence available of when a ticket that never recorded its own dates last changed. And --fix removed an H1 without always writing the title anywhere: with frontmatter absent, or title already set, the text was deleted outright while the output claimed it had been lifted, and the result passed check, so the loss was invisible. The heading is now only removed when its text is guaranteed a home.
- 2026-08-20: Review also found the hole that mattered most for check itself: every scalar rule read through ticket.scalar(), which returns nothing for a list or nested map, so the rule simply did not run. status: [building (pending Ian)] passed as clean -- the precise value this tool was built to catch, wearing brackets. A non-scalar where a single value belongs is now its own violation.
